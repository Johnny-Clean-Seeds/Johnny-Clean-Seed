# Helper Routine Loop Candidate V1

Date: 2026-05-31
Status: CANDIDATE SUPPORT / NOT DOCTRINE
WorkKey: HELPER-ROUTINE-LOOP-CANDIDATE-20260531-V1

## Aim

Give helper files a clean routine run around the house so each pass improves routing instead of adding weight.

This is not a new king gate. It is a small repeatable loop that uses the Intake Gate result, older history lessons, and current Claim + Capability Front Door work.

## Loop

0. Wear the live suit.
   - Check current Soft Suit active slots before widening.
   - Apply findings to the routine while working, not only after the report.
   - New working patterns enter as candidate/support first, then prove before stronger adoption.

1. Select one object.
   - Name the active object, source, authority basis, allowed actions, blocked actions, and close condition.

2. Taste before swallowing.
   - Classify source type, risk, runnable/code status, raw/source-ore status, helper-output status, and proof-only status.

3. Join key/hash to route.
   - Record WorkKey or controlled key, object path, SHA256 when useful, receipt purpose, route/ledger/map relation, boundary, return path, currentness, and disposition.

4. Mirror neighbor methods.
   - Ask whether a working pattern already exists in Intake Gate, Root Source Intake, Swift Scan, Rule Application Gate, Helper Shape Contract, or Source-to-House V2.
   - Copy the clean pattern, not the wording.

5. Assay helper capability.
   - A helper-facing route must state what may be read, what may be written, what must not be touched, proof required, stop condition, ledger/event row, and handoff target.

6. Do one bounded bite.
   - One repair row, one route row, one support pointer, one replay row, or one park/return trigger.
   - No broad repair while blocker-adjacent rows remain unranked.

7. Leave proof and reduce live load.
   - Receipt or event marker says what happened, what did not happen, what it proves, what it does not prove, and where to return.

8. Re-audit or park.
   - If the bite touched key/hash/routing, re-run the named read/report audit or write a return trigger for later re-audit.

## Triple-Pass Wear Pattern

Use this when the user asks for a deeper house walk or when routine gaps repeat.

1. Walls pass.
   - Walk normal room surfaces, pointers, boards, suit cards, ledgers, maps, and current work.
   - Apply the smallest clean improvement to the suit/routine before moving on.

2. Upside-down pass.
   - Invert the claims: proof as command, helper as judge, source as doctrine, hash as meaning, report as approval, Git clean as house clean, old history as live task.
   - Add guards where the inversion exposes a real failure path.

3. Deep-search pass.
   - Search outside methods only after local fit is visible.
   - Bring back method keys, not foreign authority.
   - Adopt only what maps to source custody, WIP limit, feedback, provenance, verification, helper assay, or trace/return.

Always leave a rope note for anything useful but not active.

## External Method Keys Adopted As Candidate Support

These keys were added after local fit was visible. They are support keys, not outside authority over the house.

| Method key | House use |
|---|---|

| OODA feedback | Observe, orient, decide, act, then let the result update the next orientation. |
| Cognitive-load offload | Store route evidence in files so chat does not carry the whole pile. |
| Event/receipt trail | Record state-changing moves as receipts/events that can be replayed or audited. |

## WIP Limits

Default active limits:

- one active object
- one route owner
- one helper output under assay
- one proof report
- one next action
- overflow parked with return trigger

Backpressure signs:

- same correction repeats
- helper output has ideas but no route evidence
- proof text starts acting like command
- source ore starts acting like doctrine
- old history becomes live burden
- root drop pressure turns into cleanup pressure
- another tool/save thread starts before this pass closes

Recovery:

- carry key, not furniture
- write compact handoff
- park overflow
- prove one bite
- stop or return to the current front-door work

## Helper Output Acceptance Contract

Accept helper output only if it answers:

- task
- source
- target
- relation
- toolbelt
- proof/source pointer
- boundary held
- changed state or no-change reason
- return path
- next condition

If missing, classify as `HELPER_OUTPUT_NO_ROUTE` and route to helper assay, not acceptance.

## Upside-Down Guard

Before accepting a pass result, invert the claim and see whether the house is being tricked:

| Normal claim | Upside-down failure | Guard |
|---|---|---|
| Report exists | Report is treated as approval | Report is proof surface only until a selected decision consumes it. |
| Hash exists | Hash is treated as meaning, proof, or authority | Hash proves identity/fixity only; join it to object path, receipt purpose, boundary, and return. |
| Helper output exists | Helper is treated as judge | Require helper output acceptance contract and receiver assay. |
| Source says a rule | Source is treated as doctrine | Source becomes source ore, candidate support, or proof pointer only. |
| Git status is clean | Whole house is treated as clean | Git clean is repo state only; root, local custody, and support rooms still need their own receipts. |
| Old history has value | Old history becomes live task weight | Preserve with rope note, route, and return trigger; do not carry the whole history live. |
| New pattern worked | Pattern is promoted everywhere | Adopt as candidate support immediately; promote only after proof and neighbor checks. |

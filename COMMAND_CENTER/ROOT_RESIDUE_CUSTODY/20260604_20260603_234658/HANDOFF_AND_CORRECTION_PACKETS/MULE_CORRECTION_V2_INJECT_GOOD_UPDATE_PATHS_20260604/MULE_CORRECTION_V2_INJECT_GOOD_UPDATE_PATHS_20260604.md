## What “good material” means

Good material is content that passes the project’s current proof/judgment rules and has a clear use.

Examples in this job:

- repeated-correction parent rule;
- mule-root no-loose-files child rule;
- Row 001 static fixture design;
- Row 001 inert fixture packet;
- any manifest or receipt needed to prove custody;
- any handoff correction order that should become evidence or parking material.

Good material is not automatically good because it exists.

It must be judged.

## Required judgment questions

For each root object or packet object, answer:

1. What is this?
2. Is it source, rule, fixture, proof, manifest, handoff, report, or trash-like residue?
3. Is it good, partially good, stale, duplicate, unsafe, or unclear?
4. What proves its value?
5. What lane should own it?
6. What path/pointer must be updated after moving/injecting it?
7. What downstream file needs to know the new path?
8. Is it ready for use after placement?
9. If not ready, what blocks readiness?
10. Should we pause and ask?

## Proof requirement

The mule/helper will know something is good because it tests/proves it.

Allowed proof forms depend on the object:

### Rule candidate proof

A rule candidate is proved enough for durable candidate save when:

- the triggering failure is named;
- the repeated correction is captured;
- it fits an existing house rule family or explains why it needs a new family;
- it has required behavior;
- it has a closeout/check line;
- it has boundary conditions;
- it is placed in the correct rule lane;
- a receipt or status report records it.

### Fixture proof

A fixture is proved enough for static-review use when:

- it is inert;
- file types are verified;
- no runner/launcher/helper execution exists inside;
- expected judgments are present;
- a checklist exists or is produced;
- review verdict is written;
- target-helper status remains clear.

### Path proof

Path proof requires:

- old path;
- new path;
- reason for move/injection;
- destination lane;
- references updated;
- stale path references blocked or corrected;
- manifest/receipt updated.

### Root proof

Root proof requires:

- full root inventory after work;
- list of allowed root objects;
- list of routed objects;
- list of parked/blocked objects;
- final verdict.

## Injection requirement

When a good object is moved into the project, make it ready.

“Ready” means at minimum:

- correct file/folder lane;
- clean name;
- no loose root duplicate left behind unless explicitly allowed;
- referenced by the relevant index/status/ledger/report where the project expects to find it;
- receipt or manifest says where it went;
- next worker can locate it without old root path;
- old root path is not treated as live source.

## Path update requirement

After routing/injecting, update affected paths.

Likely surfaces to update if they exist:

- current status file;
- relevant house ledger;
- relevant workbench index;
- Helper Stress Bench Row 001 report/index;
- Mule Workshop handoff/receipt lane;
- proof manifest;
- receipt;
- any README/start card for the work packet;
- any local path map that points to the old root object.

If no update surface exists, create a small path-map/report in the proper lane.

Do not leave the only usable path in chat.

## Scope discipline

Do not open a bunch of lanes just because related work exists.

Stay on the most likely direction:

1. Apply root-no-loose-files rule to actual root.
2. Inject/save the parent repeated-correction rule.
3. Inject/save the child root-no-loose-files rule.
4. Inject/review Row 001 static fixture.
5. Update paths/status/receipts.
6. Final root check.

If a new issue appears, classify it as:

- `BLOCK_NOW`
- `PARK_WITH_RETURN_TRIGGER`
- `WATCH`
- `ASK_USER`

Do not sprawl.

## Ask/stop trigger

Stop and ask the user if:

- a file’s ownership is unclear;
- moving it could destroy source custody;
- there are multiple plausible durable lanes with no clear winner;
- the work expands beyond the current rule/fixture/root-residue job;
- proof requires target-helper execution;
- a new script/runner would be needed;
- root contains user originals that might not be helper residue;
- a commit/push decision is needed and not already authorized.

Use:

`DIRECTION_UNCLEAR_STOP_AND_ASK`

Do not fake certainty.

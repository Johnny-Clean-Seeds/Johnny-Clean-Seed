The outside research supports this pretty strongly.

Records-management practice says you do not organize serious records by vibes or filenames alone; you build a file plan. A file plan is a roadmap that says what records exist, where they are stored, how they are stored, and how long they are kept. It gives users a place to file records and a way to find them later. Queen’s University’s records guidance also says records should be classified upon creation or receipt, and that an inventory is the foundation for a good file plan. ([Queen’s University][1])

The strongest records-management point is this: classify by **function**, not just by subject. Function-based file plans organize records by the work process that created or uses them; they tend to be more stable than subject-based or person-based filing, because topics and roles change faster than core functions. ([Queen’s University][1]) That maps almost perfectly to the house: do not ask only “what is this file about?” Ask “what job does this file do?”

Information architecture adds the second piece: use a controlled vocabulary. NN/g describes taxonomy as a backstage metadata structure that supports retrieval through consistent classification terms. It also distinguishes navigation, IA structure, taxonomy, and content models, which matters here because your visible folder tree should not be forced to carry every hidden classification relationship. ([Nielsen Norman Group][2]) In house language: folder path is not the whole truth; the ticket needs metadata too.

For your system, that means the receptionist should not invent new labels every run. It should use a small controlled vocabulary: `SOURCE_AUTHORITY`, `SUPPORT`, `PROOF_HISTORY`, `RECEIPT`, `HELPER_CANDIDATE`, `FAILED_RUNNER_EVIDENCE`, `OLD_LOAD`, `SYSTEM_FILE`, `UNKNOWN`, `BLOCKED`. Synonyms can be mapped later, but the live action terms must stay small.

Personal-information-management research gives the warning. Malone’s classic desk-organization study found that office organization is not only about finding things later; piles also remind people what still needs attention, and categorizing information is cognitively hard. ([ResearchGate][3]) That is the direct reason not to “clean” everything. Some root files are not just clutter. Some are reminders, unresolved work, live intake, or visible pain points. If the receptionist hides them too early, the system loses the signal.

## 15. Pattern Counterexample Discipline

Every promoted rule needs counterexamples.

Example pattern:

“Files ending in `_RECEIPT.txt` are usually proof.”

Counterexamples:

A receipt may include stale next-action language.
A receipt may prove only an old failed run.
A receipt may not be current authority.
A receipt may be in the wrong folder.
A receipt hash proves identity, not quality.

Therefore accepted rule:

`_RECEIPT.txt` strongly suggests PROOF_HISTORY or RECEIPT role, but movement and authority remain blocked until current context is checked.

Example pattern:

“PowerShell files are helper candidates.”

Counterexamples:

Some PowerShell files may be unsafe cleanup tools.
Some may be failed generated runners.
Some may be current one-shot build files.
Some may be obsolete proof/history artifacts.
Some may touch Git or delete/move files.

Therefore accepted rule:

`.ps1` suggests EXECUTABLE_HELPER_REVIEW_REQUIRED, not runnable helper.

Example pattern:

“Zero-byte files are junk.”

Counterexamples:

Zero-byte may be marker, placeholder, failed output evidence, old-load proof, or system artifact.

Therefore accepted rule:

Zero-byte is a review signal only, never deletion proof.

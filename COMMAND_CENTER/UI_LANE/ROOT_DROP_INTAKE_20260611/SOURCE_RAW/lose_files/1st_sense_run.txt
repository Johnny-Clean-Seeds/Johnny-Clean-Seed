## Batch T02 — Wider Research / Real Architecture

The outside research says there are several mature fields we should steal shapes from, but not obey as doctrine.

OpenTelemetry gives the tracing shape: a trace is made of spans, and spans represent specific operations with attributes attached to them. House translation: every gate activation should become a span-like record: gate name, input object, readable signals, trigger reason, verdict, blocked claims, next gate, and proof need. ([OpenTelemetry][1])

W3C PROV gives the custody shape: provenance models entities, activities, agents, derivations, bundles, and collections. House translation: every atom/concept/group needs to know what source entity it came from, what activity touched it, what agent/tool produced the record, and what it derives from. ([W3C][2])

OpenLineage gives the pipeline lineage shape: it tracks metadata about datasets, jobs, and runs, and its object model contains jobs and datasets. House translation: each scan run is a job, each file/atom/group is a dataset-like entity, and every gate trace is a run event. ([OpenLineage][3])

SKOS gives the concept-language shape: it is designed for knowledge organization systems such as thesauri, taxonomies, classification schemes, and subject headings. House translation: every concept group needs preferred labels, alternate labels, broader/narrower concepts, related concepts, forbidden synonym collapses, and scope notes. ([W3C][4])

MinHash and locality-sensitive hashing give the near-duplicate shape: MinHash estimates similarity between sets and was used for duplicate web-page detection; the useful house translation is “find near-same material without requiring exact hash match.” ([Wikipedia][5])

SimHash gives another near-duplicate shape: unlike cryptographic hashes, similar items can produce fingerprints with small Hamming distance, which is useful for near-duplicate detection. House translation: SimHash can help find “same section rewritten” or “same rule with light wording drift,” but it cannot decide concept truth. ([Google Research][6])

Sentence-BERT gives the semantic-neighborhood shape: it creates sentence embeddings that can be compared with cosine similarity for semantic search and clustering. House translation: embeddings help find “same idea, different words,” but they are dangerous if allowed to group material without gate/proof checks. ([ACL Anthology][7])

HDBSCAN gives the outlier shape. Its own documentation explicitly treats real data as messy, with outliers, corrupt data, and noise; it can leave small groupings as noise instead of forcing everything into a cluster. House translation: this is exactly what we need for leftovers. Not everything should be grouped. Some residue must stay residue. ([HDBSCAN][8])

BERTopic gives the interpretable-topic shape: it combines transformer-style embeddings with c-TF-IDF, where c-TF-IDF finds what makes one cluster different from another. House translation: after grouping atoms, the system needs to name each group by what distinguishes it, not by the loudest common word. ([Maarten Gr GitHub Pages][9])

Elastic Common Schema gives the event-shape idea: an event records something that happened, with time and context; tracing fields include trace IDs and span IDs so related events can be tied together. House translation: every gate event needs trace ID, object ID, parent span, gate, action, result, timestamp, and relation to the next gate. ([Elastic][10])

## Batch T04 — Concept Grouping Court / Group Hash Stack / False Match Blockers

The weak version says:

`find similar things and group them`

The real version says:

`make every proposed group stand trial before it becomes a house concept`

That is the missing depth.

A concept group is dangerous if it forms too easily. Bad grouping is worse than no grouping, because it gives the house false confidence. A bad group can make unrelated things look like one rule, make one repeated word look like a pattern, hide contradictions, or let a support card become doctrine.

So the grouping system needs a court.

Not a sorter.

A court.

The outside systems give useful parts. SKOS gives the concept vocabulary shape: concepts can have preferred labels, alternative labels, hidden labels, and semantic relations such as broader/narrower/related. ([W3C][1]) PROV gives the lineage shape: entities are used and produced by activities, with agents influencing or bearing responsibility for those activities. ([W3C][2]) OpenTelemetry gives the trace shape: a tracer creates spans that carry information about a specific operation. ([OpenTelemetry][3])

House translation:

`SKOS = concept naming skeleton`

`PROV = custody / lineage skeleton`

`TRACE SPANS = gate movement skeleton`

But the house adds the missing judgment:

`Mercury names.`
`Venus checks relation.`
`Saturn blocks overclaim.`
`Earth proves material fact.`
`Neptune catches false similarity fog.`
`Pluto watches repeated hidden-parent groups.`

The existing house boundary already says not to carry every ledger, not to link everything to everything, not to treat Chat Drop as authority, and not to treat a link as proof.  That is exactly the anti-bloat law for grouping.

# 1. Concept grouping must begin from atoms, not files

A full file is usually too big to group cleanly.

One file can contain:

`source material`

`rules`

`examples`

`receipts`

`hashes`

`warnings`

`blocked verdicts`

`metaphors`

`future ideas`

`dead language`

`current law candidates`

If we group whole files, we smear all of that together.

The grouping unit should be the **atom**.

An atom can be:

`one rule line`

`one verdict block`

`one heading section`

`one receipt fact`

`one proof claim`

`one blocked action`

`one example`

`one contradiction`

`one gate card field`

`one leftover phrase`

The file becomes a container. The atom becomes the judged unit.

So the pipeline is:

`FILE`
→ `ATOMS`
→ `FINGERPRINTS`
→ `CANDIDATE LINKS`
→ `GROUP COURT`
→ `CONCEPT CARD`
→ `RESIDUE BOARD`

Not:

`FILE`
→ `GROUP`

That shortcut is how the house gets mush.

# 2. The group hash stack

A group needs multiple signatures. One hash is not enough.

`EXACT_HASH`

This proves exact identity. It answers: “Is this exact atom the same bytes/text as that exact atom?”

Use for custody.

Do not use for concept family.

`NORMALIZED_HASH`

This proves near identity after harmless normalization: line endings, whitespace, casing, markdown bullets.

Use for “same text with formatting drift.”

Do not use for semantic sameness.

`SHINGLE_SIGNATURE`

This breaks text into overlapping chunks.

Use for near-duplicate paragraphs.

Good for finding copied/reworded sections.

`MINHASH_SIGNATURE`

MinHash is used to estimate set similarity compactly; the standard use is comparing sets such as document shingles without comparing every raw element. ([OpenTelemetry][4])

House use:

`near-same wording family`

Not:

`same rule`

`SIMHASH_SIGNATURE`

SimHash is built so similar inputs can have fingerprints close by Hamming distance, which is useful for near-duplicate detection rather than cryptographic identity. ([OpenTelemetry][4])

House use:

`near-duplicate / drifted-copy detection`

Not:

`same meaning proven`

`TFIDF_SIGNATURE`

TF-IDF downweights terms that occur too often and helps surface terms that distinguish one document/atom from another; common implementations also allow stop-word and max-document-frequency controls. ([OpenTelemetry][4])

House use:

`important word signal`

`cheap word suppression`

Not:

`final concept grouping`

`SEMANTIC_SIGNATURE`

Sentence embedding methods such as Sentence-BERT are designed to compare sentence meaning efficiently with similarity measures such as cosine similarity. ([OpenTelemetry][4])

House use:

`same idea / different wording candidate`

Not:

`same authority`

`ROLE_SIGNATURE`

This is house-specific.

It says what the atom is doing:

`RULE`

`SOURCE`

`RECEIPT`

`PROOF_CLAIM`

`BOUNDARY`

`COMMAND`

`EXAMPLE`

`RISK`

`VERDICT`

`CANDIDATE`

`PARKED`

Two atoms with similar words but different roles should not merge automatically.

Example:

`hash proves identity`

as a rule

and

`SHA256: ABC...`

as a receipt fact

belong near each other, but they are not the same thing.

`GATE_SIGNATURE`

This is also house-specific.

It records which gates the atom wakes.

Example:

`MERCURY + SATURN + EARTH`

means word/proof/claim boundary.

`MOON + TOKEN_CUSTODY + EARTH`

means custody/hash/receipt.

`ECHO + PLUTO + MERCURY`

means repeated shape/root/name.

This may be stronger than semantic similarity.

`PROOF_SIGNATURE`

What kind of proof does this atom need?

`PATH_EXISTS`

`HASH_MATCH`

`RUNTIME_OUTPUT`

`SCREEN_OBSERVATION`

`USER_ACCEPTANCE`

`SOURCE_CITATION`

`REPEATED_CASES`

`BEFORE_AFTER_DIFF`

If two atoms need different proof, they should not fully merge.

`RISK_SIGNATURE`

What false move does this atom block?

`HASH_EQUALS_QUALITY`

`RECEIPT_EQUALS_TRUTH`

`STATIC_VERIFY_EQUALS_RUNTIME`

`CANDIDATE_EQUALS_DOCTRINE`

`PARKED_EQUALS_ACCEPTED`

`CUSTODY_EQUALS_CLEANUP`

This is one of the strongest grouping signals.

If two atoms block the same false move, they are probably family.

# 4. The false match blockers

The court needs hard blockers.

`CHEAP_WORD_BLOCKER`

Reject grouping if the only shared terms are common words or generic house words.

Examples:

`the`

`and`

`high`

`good`

`gate`

`file`

`rule`

`clean`

`proof`

`source`

Some of these words are important in context, but not alone.

`clean` alone is not enough.

`clean + root + SOURCE_RAW + custody + no mutation`

is enough.

`SINGLE_SIGNAL_BLOCKER`

One signal cannot create a strong group.

One shared word, one shared gate, one shared role, or one shared embedding neighborhood is only a candidate link.

Strong group requires multiple independent matches.

`ROLE_MISMATCH_BLOCKER`

A receipt and a doctrine rule cannot merge just because both mention proof.

They can be related, but not same group unless the group is explicitly a relation group.

`PROOF_MISMATCH_BLOCKER`

If one atom requires runtime proof and another requires hash proof, they should not merge as the same proof group.

They may both belong under broader concept:

`PROOF_SCOPE_CONTROL`

but one is:

`HASH_IDENTITY_PROOF`

and the other is:

`RUNTIME_BEHAVIOR_PROOF`

`AUTHORITY_MISMATCH_BLOCKER`

If one atom is source/support and another is active/current, they cannot merge without authority review.

This protects against:

`support card = doctrine`

`receipt = rule`

`web source = house law`

`STATUS_CONFLICT_BLOCKER`

If one atom says `NOT_DOCTRINE` and another says `ACTIVE_RULE`, the group cannot be accepted until Mercury/Saturn resolve the contradiction.

`TIME_DRIFT_BLOCKER`

Two atoms may have been true at different times.

A stale rule and a current rule can look similar.

The court must ask:

`current?`

`superseded?`

`proof only?`

`parked?`

`active candidate?`

The house drift review already used hashes to catch version/copy mismatch and explicitly warned that hashes identify artifacts and copy drift, not quality.  That same rule applies here: time/version identity is not quality.

`METAPHOR_BLOCKER`

A metaphorical similarity cannot become a rule group without behavior.

Example:

“nervous system,” “signals,” and “trace” are related language.

But the group is not accepted until there are fields, triggers, outputs, and pass-forward rules.

`EMBEDDING_FOG_BLOCKER`

Semantic embeddings can put things near each other because they “feel related.”

That is useful scent.

It is not judgment.

Neptune must mark:

`SEMANTIC_NEARNESS_NOT_PROOF`

`GRAPH_SPIDERWEB_BLOCKER`

If the group creates too many links to too many concepts, it is not a clean group. It is a spiderweb.

The Edward file already says the map is relation grammar, not a spiderweb, and that tool-bearing tunnels need proof need, leave-behind, return path, and stop condition. 

So a group must have typed relations, not infinite relations.

## Batch T05 — Residue Board / Leftover Intelligence / Ungrouped Material as Signal

The residue is not the trash pile.

The residue is where the house finds missing organs.

That is the main correction.

A normal clustering system tries to reduce leftovers. It treats unclustered material as noise, outliers, or errors. That is useful technically, but too weak for the house. HDBSCAN, for example, is explicitly a clustering method that can identify dense regions and leave non-fitting material as noise; scikit-learn’s outlier/novelty docs also frame unusual observations as abnormal or deviant relative to learned structure. ([HDBSCAN][1])

House translation:

`NOISE` is not automatically junk.

`OUTLIER` is not automatically error.

`LEFTOVER` is not automatically trash.

Residue is material that failed the current grouping court. That failure may mean the atom is useless. But it may also mean the current house vocabulary is missing a word, missing a gate, missing a room, missing a route, missing a proof class, or hiding a parent problem.

So the Residue Board is not a cleanup report.

It is the house’s **unplaced-signal bench**.

The existing house grammar already says Edward mode must end by routing outputs to `ADOPT / ADAPT / PARK / BLOCK / PROOF / LEAVE-BE`, and it explicitly warns that cutting without sewing is destruction while sewing without cutting is bloat.  That rule becomes the residue law: leftovers are not thrown away; they are cut out of false groups, then sewn to the right holding state.

# 1. What creates residue

Residue is created when an atom fails clean grouping.

An atom becomes residue when:

`it does not match any concept group`

`it matches too many groups`

`it matches only by cheap words`

`it has high semantic similarity but wrong role`

`it has the right role but wrong proof burden`

`it has the right gate signature but wrong authority level`

`it bridges two groups without belonging fully to either`

`it contradicts the group it almost entered`

`it is a repeated weak signal but not yet root proof`

`it appears important but lacks a stable name`

`it uses metaphor that has no system behavior yet`

`it exposes a new mechanism old gates cannot hold`

That last point matters. A leftover can be the first sign of Uranus: old categories are not enough.

## Batch T06 — Lineage / Provenance / Chain of Custody

This is the part that keeps the tracer from becoming hallucinated memory.

A concept group is not trustworthy unless the house can answer:

`Where did this atom come from?`
`What source held it first?`
`What activity touched it?`
`What tool read it?`
`What gate interpreted it?`
`What group absorbed it?`
`What residue board rejected it?`
`What proof supports it?`
`What proof does not support it?`
`What later artifact inherited it?`

Without lineage, the concept grouper becomes dangerous. It can group ideas, but it loses custody. Then the house starts saying “we know this” without knowing where “this” came from.

The outside research gives the skeleton. W3C PROV says provenance describes the use and production of entities by activities, with agents influencing those activities. House translation: every source, atom, trace, group, residue item, and final report must know its entity/activity/agent chain. ([W3C][1])

OpenLineage gives another useful shape: it tracks metadata about datasets, jobs, and runs, so users can understand root cause and impact of changes. House translation: the trace scan is a job, each scan execution is a run, and each file/atom/group is a dataset-like object with lineage. ([OpenLineage][2])

SLSA gives the artifact-integrity pressure: provenance should explain where, when, and how something was produced. House translation: a concept card must not only say what it means; it must show how it was generated from source atoms, traces, and court verdicts. ([SLSA][3])

CycloneDX gives the bill-of-materials pressure: modern systems need inventories of components and relationships for supply-chain visibility. House translation: the concept grouper needs a “bill of concepts / bill of atoms / bill of traces,” not just a pretty summary. ([OWASP Foundation][4])

Now the house version.

The house already says `BONE` identifies structural proof, receipt, commit, and trust custody, while `NERVE` traces the signal path from front door to target and back. It also says `LOCK` saves only after proof. 

So lineage is Bone + Nerve + Moon + Earth + Saturn.

`MOON` preserves source.

`BONE` checks structural proof.

`NERVE` traces movement.

`EARTH` proves material fact.

`SATURN` blocks unsupported claims.

Lineage is not a side note. It is the skeleton of the whole tracer.

# 2. Lineage layers

There are six lineage layers.

`SOURCE LINEAGE`

Where the raw material came from.

Examples:

file path, upload name, repo path, chat paste, web source, command log, receipt.

`ATOM LINEAGE`

Where each atom came from inside the source.

Examples:

heading path, line span, paragraph ID, table row, code block.

`TRACE LINEAGE`

Which gates touched the atom.

Examples:

Intake span, Mercury span, Saturn span, Earth span.

`GROUP LINEAGE`

Which concept group accepted the atom.

Examples:

`C_STATIC_PROOF_VS_RUNTIME_PROOF`

`C_CUSTODY_PLACEMENT_NOT_CLEANUP`

`RESIDUE LINEAGE`

Why the atom did not group.

Examples:

false match, bridge, contradiction, orphan, fog, root signal.

`ARTIFACT LINEAGE`

What final object inherited this material.

Examples:

concept card, residue board, merge report, spec file, handoff, future script output.

Each layer must be traceable backward.

If a concept card says:

`Hash proves identity only`

it should point to the atoms and receipts that created that rule family. It should not float as “common sense.”

# 7. The source-set hash

Every scan report needs a source-set hash.

Not just hashes of files.

A source-set hash is a hash of the input list plus each source hash.

Example:

`SourceSetManifest`

`1. file A | hash A`

`2. file B | hash B`

`3. file C | hash C`

Then hash that manifest.

Why?

Because if the report says “I scanned the candidate, addendum, web-check, and receipt,” the house needs proof that the exact set was known.

This blocks:

`silent source swap`

`missing source`

`extra source`

`using parked drift file`

`accidental old version`

It does not prove the report is good. It proves what input set the report claims to have used.

That matches the house’s Earth rule: hashes prove identity/copy integrity, not quality. The Earth material explicitly blocks hash-match from becoming quality and separates file existence, static verify, runtime pass, and acceptance pass.

# 13. The line between lineage and proof

Lineage is not proof by itself.

Lineage says:

`This came from there.`

Proof says:

`This claim is supported by that evidence.`

A perfect lineage chain can still lead to a weak claim.

Example:

A concept card may have perfect lineage from five atoms, but if all five atoms are speculative, the concept remains candidate.

So every lineage card needs:

`LineageStrength`

and:

`ClaimStrength`

They are different.

`LineageStrength`

How well we know where the material came from.

`ClaimStrength`

How well the evidence supports the claim.

Possible states:

`LINEAGE_STRONG / CLAIM_WEAK`

Common for ideas with good custody but no test.

`LINEAGE_WEAK / CLAIM_BLOCKED`

Cannot trust the claim because parentage is unclear.

`LINEAGE_STRONG / CLAIM_STRONG_WITH_SCOPE`

Best case.

`LINEAGE_STRONG / CLAIM_OVERREACH`

Good source chain, bad conclusion.

This distinction is critical.

## Batch T07 — Claim Scope / DoesNotProve Engine

This is the part that prevents the whole tracer from lying politely.

The tracer can find atoms.
The grouper can build concept families.
The lineage system can show where material came from.
But none of that is enough unless every claim is forced to say:

`What exactly do I prove?`

and:

`What exactly do I not prove?`

That second field is not decoration. It is the immune system.

The house already has the core word law for this: `fit != pass`, `source raw != trusted`, `custody placement != cleanup`, `installed != launched`, `copied != launched`, `verified != accepted`, `hash match != quality`, `receipt exists != proof pass`, `repo clean != runtime pass`, `commit pushed != system correct`, `candidate != doctrine`, `vision != proof`, and `exists != works`. 

So Batch T07 builds the engine that enforces those splits everywhere.

The outside research supports the shape, but does not replace the house. OpenTelemetry gives the span/attribute model: traces are made from spans, and span attributes carry structured facts about a specific operation. ([OpenTelemetry][1]) W3C PROV gives the entity/activity/agent chain: material comes from entities, activities act on entities, and agents are responsible for or influence activities. ([W3C][2]) SLSA provenance says provenance describes where, when, and how software artifacts were produced; that maps cleanly to artifact origin, not artifact quality. ([SLSA][3]) CycloneDX’s composition model tracks constituent parts and completeness state, which maps well to “what is included / incomplete / unknown,” not “therefore the system works.” ([CycloneDX][4])

House translation:

`TRACE SPAN = what one gate saw and did`

`PROVENANCE = where the evidence came from`

`COMPOSITION = what parts are present or missing`

`CLAIM SCOPE = what the evidence is legally allowed to support`

`DOES_NOT_PROVE = what must not be inferred`

# 1. Core law

`EVIDENCE NEVER SPEAKS GLOBALLY.`

Evidence speaks only to one claim, at one scope, under one route, with one proof shape.

A hash can speak to identity.

A path check can speak to existence.

A file count can speak to static completeness.

A receipt can speak to recorded action.

A launch log can speak to runtime behavior.

A user approval can speak to acceptance.

A promotion receipt can speak to authority.

But no evidence token gets to say everything.

The house version:

`Every proof object must carry a claim-scope card.`

No claim-scope card means the evidence is not allowed to close anything stronger than raw existence.

# 4. The claim ladder

This is the proof ladder.

The house must know which rung a claim is on.

`RUNG 0 — MENTION`

Something was mentioned.

Proves:

`term appeared`

Does not prove:

meaning, truth, action, existence outside text.

Example:

A file mentions `runtime pass`.

Does not prove runtime pass.

`RUNG 1 — EXISTENCE`

A file/path/object exists.

Proves:

`object exists at observed location`

Does not prove:

quality, correctness, safety, runtime, acceptance.

Earth owns this.

`RUNG 2 — IDENTITY`

A hash or exact signature matches.

Proves:

`same bytes/content as prior recorded object`

Does not prove:

quality, truth, safety, fit, runtime.

The drift review already states this cleanly: hashes identify artifacts and help detect copy drift, but they do not prove quality. 

`RUNG 3 — CUSTODY`

The object is preserved in a known place with receipt/hash.

Proves:

`the object was housed/preserved`

Does not prove:

trusted, accepted, cleaned, reviewed, safe.

Moon + Token Custody + Earth own this.

`RUNG 4 — STATIC STRUCTURE`

Files copied, counts match, expected names present, schema parsed.

Proves:

`static placement or structural expectation`

Does not prove:

runtime behavior, user acceptance, future correctness.

Earth + Mercury + Saturn own this.

`RUNG 5 — CONTENT REVIEW`

Someone or some gate reviewed content and made a bounded judgment.

Proves:

`reviewed under stated criteria`

Does not prove:

runtime, action authority, doctrine.

Mercury/Saturn/Venus/Neptune may own parts.

`RUNG 6 — ACTION AUTHORITY`

User/gate explicitly authorized a bounded action.

Proves:

`action may be attempted within scope`

Does not prove:

action succeeded.

Mars + Saturn own this.

`RUNG 7 — ACTION EXECUTION`

Command/action ran and output was captured.

Proves:

`action was executed and produced captured result`

Does not prove:

result is accepted, safe forever, or doctrine.

Earth owns result; Mars owns force trace.

`RUNG 8 — RUNTIME BEHAVIOR`

System launches/runs/opens/behaves in observed test.

Proves:

`runtime behavior under tested condition`

Does not prove:

all future behavior, user acceptance, doctrine.

Earth owns this.

`RUNG 9 — USER ACCEPTANCE`

User accepts a result.

Proves:

`human acceptance of that result/scope`

Does not prove:

technical correctness outside the accepted scope.

Sun/Venus/Saturn/Earth may be involved depending on claim.

`RUNG 10 — REPEATED PROOF`

Multiple cases repeat under controlled conditions.

Proves:

`pattern has repeated support`

Does not prove:

universal rule.

Jupiter can now consider growth. Saturn still blocks overreach.

`RUNG 11 — PROMOTION AUTHORITY`

A candidate is explicitly promoted through the right gate.

Proves:

`it is active within declared scope`

Does not prove:

permanent doctrine or universal truth.

Jupiter + Saturn + Final Judge own this.

`RUNG 12 — DOCTRINE`

Only if the house has a formal doctrine promotion path.

Proves:

`house doctrine within declared version/scope`

Does not prove:

immune to future revision.

This rung is blocked by default.

## Batch T08 — Gate Memory / Pass-Forward Packets

The tracer is not complete until each gate leaves a **memory packet** for the next gate.

That is the missing movement.

A gate cannot just produce a verdict and disappear. The next gate needs to know:

`why it received the object`

`what the prior gate already decided`

`what the prior gate blocked`

`what proof burden is still open`

`what claim scope is locked`

`what it must not reopen`

`what it is allowed to add`

That means the object does not travel alone.

The object travels with a **Pass-Forward Packet**.

Outside systems give useful pressure here. Event sourcing stores state changes as a sequence of events, so the current state can be reconstructed from the event history; the useful house translation is not “build event sourcing now,” but “do not lose the path of decisions that produced the current state.” ([martinfowler.com][1]) Event-driven architecture also separates producers, consumers, and channels; house translation: a gate produces a packet, the next gate consumes it, and the rope/channel controls legal movement. ([Microsoft Learn][2]) PROV keeps the entity/activity/agent chain; house translation: a pass-forward packet must preserve what entity was judged, what activity judged it, and what agent/gate produced the judgment. ([W3C][3])

The house already has the internal rule for this: carry one active object, one proof pointer, and one next condition, not the whole pile.  The tool grammar also says Nerve traces the signal path from front door to target and back, Bone checks proof/receipt/trust custody, and Sew reconnects with typed tunnel, proof, key, boundary, and return path. 

So this batch defines the thing that travels.

# 1. Core law

`NO_GATE_HANDOFF_WITHOUT_PACKET.`

A gate is not finished until it creates a packet.

A packet is not a summary. It is a bounded state transfer.

The packet tells the next gate:

`This is the object.`
`This is the current legal status.`
`This is what I decided.`
`This is what I did not decide.`
`This is what I blocked.`
`This is what proof is still missing.`
`This is why you are next.`
`This is where you must stop.`

Without that packet, the next gate starts from memory or vibe. That is where drift enters.

# 2. Why normal summaries are too weak

A normal summary says:

`Mercury checked the words. Saturn needs proof.`

That is not enough.

A pass-forward packet says:

`Mercury found the word “verified” near a runtime claim.`
`Mercury defined verified as static/copy/hash evidence only in this context.`
`Mercury blocked “verified = runtime pass.”`
`Mercury passed to Saturn because the claim is stronger than the evidence.`
`Open proof: launch/runtime output.`
`DoesNotProve: file count/hash/receipt do not prove UI works.`

Now Saturn knows exactly what to do.

Saturn should not reread the whole file and decide from scratch. Saturn receives Mercury’s scoped claim and adds Saturn’s own authority/proof judgment.

That is the difference between a pile and a nervous system.

# 3. Packet classes

There should be several packet types, not one giant packet.

`OBJECT_STATE_PACKET`

`GATE_MEMORY_PACKET`

`CLAIM_SCOPE_PACKET`

`PROOF_BURDEN_PACKET`

These packets can be represented together in a trace log later, but conceptually they are different organs.

# 5. Packet rule: append, do not overwrite

Every gate appends its packet.

It does not erase prior packets.

That is important.

If Mercury defines `candidate != doctrine`, Saturn should not overwrite that. Saturn adds:

`promotion blocked until proof/promotion authority`

Then Earth adds:

`file exists/hash matches only`

Then Final Judge adds:

`not doctrine, proof route`

If packets overwrite each other, the chain loses why the current state exists.

The event-sourcing analogy fits here: state is reconstructed from a sequence of recorded events, not from one vague final sentence. ([martinfowler.com][1])

House law:

`GATE MEMORY IS APPEND-ONLY DURING A TRACE RUN.`

A later gate may supersede a prior packet only by explicitly saying:

`SUPERSEDES_PACKET: ___`

`Reason: ___`

`Proof: ___`

No silent replacement.

# 6. Packet rule: next gate inherits limits

The next gate does not receive a blank object.

It receives the object plus inherited limits.

Example:

Mercury packet:

`BlockedClaim: verified = runtime pass`

Saturn receives that as inherited law for this object.

Saturn cannot say:

`verified means good enough`

unless it explicitly challenges Mercury’s packet, and it would need evidence.

Saturn adds:

`ProofRequired: runtime launch output`

Earth receives both:

`verified is scoped to static proof`

and:

`runtime proof required`

Earth then knows not to prove the wrong thing.

This is how the next gate sees correctly.

Each gate changed the envelope, not the object.

## Batch T09 — Gate Runtime / Expected-vs-Actual Replay

This batch is where the tracer stops being a theory.

Up to now, we defined the parts:

`gate trace spans`
`concept grouping court`
`residue board`
`lineage chain`
`claim-scope engine`
`pass-forward packets`

Now we need the replay engine that proves whether the gates actually move correctly.

Not live action.

Not source mutation.

Not whole-house crawl.

This is a **read-only replay** of gate behavior over a selected source set.

The outside pattern is clear. OpenTelemetry treats trace data as spans connected inside traces, so a system can see what operation happened and how it relates to other operations. OpenLineage events are additive across a run’s lifecycle, meaning different metadata can be collected at different moments without replacing the whole run state. Event sourcing gives the replay idea: store changes as a sequence of events so prior/current state can be reconstructed from that event log. Hypothesis stateful testing gives the testing pressure: rules can be chained in one run, and later rules interact with earlier state. House translation: replay each atom through gate rules, append packet events, reconstruct the object’s legal state, then compare expected movement against actual text/status/verdict movement. ([OpenTelemetry][1])

# 1. Core law

`REPLAY DOES NOT ACT.`

Replay does not run scripts.
Replay does not edit files.
Replay does not clean folders.
Replay does not promote doctrine.
Replay does not commit or push.
Replay does not decide runtime behavior unless runtime evidence is already present.

Replay reads a bounded source set and asks:

`Given this source material, which gates should have triggered?`

Then:

`Which gates actually appear to have triggered in the material?`

Then:

`Where did the gate path break?`

That is the whole point.

The replay engine is not trying to “be smart.” It is trying to expose mismatches.

# 2. Expected vs actual

The replay has two sides.

`EXPECTED`

What the house rules say should happen.

Example:

If an atom says `hash verified, system works`, expected triggers are:

`TOKEN_CUSTODY`
`MERCURY`
`SATURN`
`EARTH`

because hash language, claim wording, proof overreach, and exact material evidence are all active.

`ACTUAL`

What the source text/status/verdict actually says happened.

Example:

If the source only says:

`EARTH_HASH_MATCH_CONFIRMED`

then actual trigger is Earth only.

Replay result:

`MISSING_TRIGGER: TOKEN_CUSTODY`

`MISSING_TRIGGER: MERCURY`

`MISSING_TRIGGER: SATURN`

`OVERCLAIM_RISK: hash treated as broad proof`

That is a real finding.

A gate is not linked well if the expected side and actual side disagree in important ways.

# 3. Replay is not one pass

The replay should run in layers.

`PASS 1 — SOURCE SET LOCK`

Lock the exact source files.

Output:

`SOURCE_SET_MANIFEST`

Fields:

`path`

`hash`

`role`

`authority state`

`included/excluded`

`DoesNotProve`

This blocks source drift.

`PASS 2 — ATOM SPLIT`

Split each source into atoms.

Atoms are headings, sections, rule lines, verdict blocks, receipt facts, claims, code blocks, command lines, table rows, examples, and residue fragments.

Output:

`ATOM_LEDGER`

`PASS 3 — EXPECTED TRIGGER PASS`

Run trigger dictionaries against every atom.

Output:

`EXPECTED_TRIGGER_LEDGER`

This says what gates should wake.

`PASS 4 — ACTUAL TRIGGER PASS`

Extract actual gate language from the atom.

Look for:

explicit gate names

verdict words

blocked actions

DoesNotProve lines

next-gate lines

proof-needed lines

authority-state words

Output:

`ACTUAL_TRIGGER_LEDGER`

`PASS 5 — DIFF COURT`

Compare expected vs actual.

Output:

`EXPECTED_ACTUAL_DIFF_REPORT`

`PASS 6 — PACKET REPLAY`

Build pass-forward packets in sequence.

Output:

`PACKET_CHAIN_LEDGER`

`PASS 7 — STATE RECONSTRUCTION`

Reconstruct the object’s legal state from packet chain.

Output:

`OBJECT_MEMORY_STACK`

Event sourcing supports this reconstruction idea: the current state can be derived by replaying the event sequence rather than trusting one final summary. ([martinfowler.com][2])

`PASS 8 — INVARIANT CHECK`

Check laws that must always hold.

Output:

`INVARIANT_FAILURE_REPORT`

`PASS 9 — RESIDUE HANDOFF`

Anything unmatched, contradictory, or ungroupable goes to Residue Board.

Output:

`RESIDUE_REPLAY_BOARD`

# 4. Replay modes

There should be modes.

`TRACE_ONLY_MODE`

Reads source and shows expected/actual trigger differences.

No grouping.

No residue court.

Use when the source set is new or risky.

`GROUP_REPLAY_MODE`

Runs trace plus concept grouping.

Use after source set is trusted.

`PACKET_REPLAY_MODE`

Runs gate packet chain and reconstructs state.

Use to test pass-forward.

`FIXTURE_MODE`

Runs synthetic test atoms through the rules.

Use to test the tracer itself.

`COUNTERFACTUAL_MODE`

Asks “what would have happened if this old phrase stayed?”

Example:

If old run card says `support toolbelt used if triggered`, expected replay should flag:

`SUPPORT_MEMBRANE_MISSING`

`LAYER_ECHO_NOT_FIRST`

This is useful but should remain later-stage, because counterfactuals can create fog.

# 5. Replay mismatch classes

The replay engine needs exact failure names.

`MISSING_TRIGGER`

A gate should have fired but did not appear.

Example:

Hash used as proof, but Token Custody missing.

`OVER_TRIGGER`

A gate fired without enough reason.

Example:

Pluto root dive from one weak signal.

`WRONG_GATE`

A different gate took the job.

Example:

Saturn tries to prove runtime instead of Earth.

`EARLY_GATE`

A later gate fires before required prior gate.

Example:

Mars action before Saturn authority.

`LATE_GATE`

A gate fires only after damage.

Example:

Moon custody after source was rewritten.

`SWALLOWED_GATE`

One gate absorbs another gate’s job.

Example:

Mercury handles both word definition and proof closure.

`SHADOW_UNCHECKED`

Gate’s false-authority risk appears but no counterweight fires.

Example:

Jupiter growth language appears, but Saturn proof boundary missing.

`PACKET_BREAK`

A gate produces a verdict but no pass-forward packet.

Example:

Mercury says `word collision` but does not pass proof burden to Saturn.

`PACKET_OVERWRITE`

Later packet silently erases earlier claim scope.

Example:

Final Judge says `done` after Earth said `runtime not proven`.

`PROOF_RUNG_MISMATCH`

Claim is on a higher proof rung than evidence supports.

Example:

Receipt existence used as runtime pass.

`DOES_NOT_PROVE_MISSING`

Evidence has no explicit blocked stronger claims.

Example:

Hash shown without saying hash does not prove quality.

`RESIDUE_UNHANDLED`

Ungrouped atom not classified.

`FALSE_GROUP_ACCEPTED`

Concept group accepted from cheap word/weak signal.

`ROUTE_WITHOUT_STOP`

Next gate selected but no stop condition.

These names become the tracer’s error language.

# 6. Replay invariant laws

Invariants are laws that must hold on every replay.

`NO_ACTION_WITHOUT_MARS_AND_SATURN`

If an atom requests run/delete/install/commit/push/mutate, Mars and Saturn must appear before action is considered legal.

`NO_RUNTIME_WITHOUT_EARTH`

No runtime claim closes without Earth evidence.

`NO_DOCTRINE_WITHOUT_PROMOTION`

No candidate/support/report/source becomes doctrine from grouping or receipt alone.

`NO_HASH_AS_QUALITY`

Hash proves identity/copy only.

`NO_RECEIPT_AS_GLOBAL_PROOF`

Receipt proves only the recorded action/status within scope.

`NO_SOURCE_AS_AUTHORITY`

External/internal source is not active law without review/promotion.

`NO_GROUP_FROM_CHEAP_WORD`

Concept group cannot form from one generic term.

`NO_LEFTOVER_DELETE`

Residue cannot be deleted as junk.

`NO_PARK_WITHOUT_RETURN_TRIGGER`

Parking must have return trigger unless marked `LEAVE_BE`.

`NO_GATE_SWALLOWING`

A gate may not decide outside its domain without routing to owner gate.

`NO_PACKETLESS_HANDOFF`

Gate handoff must create a packet.

`NO_FINAL_DONE_WITH_OPEN_PROOF`

Final Judge cannot say done while proof burden remains open.

`NO_WHOLE_HOUSE_CRAWL_IN_V0_1`

The first tracer version must stay on small source sets.

These invariants are what make replay hard instead of decorative.

## Batch T10 — Fixture Forge / Shape Bench

This batch builds the test cases the tracer must pass before it is trusted on real house material.

A tracer that has no fixtures is just another confident report writer.

Fixtures are the fake-but-controlled objects we feed into the tracer to see whether the gates wake correctly. They are not real work. They are not source truth. They are test shapes.

The house already has the right testing attitude: one active object, one proof pointer, one next condition, smoke-break reset between waves, and no whole-pile carry.  The tool grammar also says Scissor cuts false/stale material, Sew reconnects with proof/boundary/return path, Bone checks proof custody, Nerve traces signal path, and Lock saves only after proof. 

So the Fixture Forge is:

`NERVE` — trace signal path.

`BONE` — check proof shape.

`SCISSOR` — cut false routes.

`SEW` — connect expected gate chain.

`SATURN` — block overclaim.

`EARTH` — verify the tracer result, not the real-world claim.

# 1. Core law

`NO TRACER TRUST WITHOUT FIXTURE PASS.`

Before the tracer scans real source, it must pass known traps.

A fixture is a controlled atom where we already know the correct gate path.

The fixture asks:

`Does the tracer wake the right gates?`

`Does it block the right false claim?`

`Does it build the right pass-forward packet?`

`Does it assign the right proof burden?`

`Does it avoid overtriggering?`

`Does it avoid deleting or promoting residue?`

`Does it return a clean verdict?`

If it cannot pass the fixture bench, it is not ready for real source.

## Batch T12 — Read-Only Tool Spec / First Local Script Behavior

This batch defines the first local tool shape. Not the code yet. The point is to make the behavior contract so tight that when code is written, it cannot quietly become a watcher, automation, cleanup tool, graph database, doctrine writer, or whole-house crawler.

The tool name should be:

`READ_ONLY_GATE_TRIGGER_TRACER_SMALL_LAB_V0_1`

Long name:

`READ_ONLY_HOUSE_GATE_TRIGGER_TRACER_AND_CONCEPT_GROUPER_SMALL_LAB_V0_1`

Status:

`READ_ONLY_TOOL_SPEC / NOT_DOCTRINE / NOT_AUTOMATION / NOT_WATCHER / NOT_CLEANUP / NOT_GRAPH_DATABASE / NOT_WHOLE_HOUSE_CRAWL`

The tool’s first job is not to “understand the whole house.”

The first job is narrower:

`Read an approved small source set.`
`Hash the exact inputs.`
`Split content into atoms.`
`Detect expected gate triggers.`
`Extract actual gate language.`
`Compare expected vs actual.`
`Build gate memory packets.`
`Scope claims and DoesNotProve lines.`
`Group obvious concept families.`
`Classify residue.`
`Write reports only.`
`Stop.`

No mutation. No action. No cleanup. No source rewrite. No doctrine promotion.

# 1. Core tool law

`THE TOOL READS AND REPORTS ONLY.`

It must not:

`edit source files`

`move source files`

`delete source files`

`archive source files`

`dedupe source files`

`rewrite source files`

`normalize source files in place`

`execute discovered scripts`

`run discovered commands`

`install anything`

`start a watcher`

`create a background task`

`crawl the whole repo`

`touch ACTIVE_GUIDES`

`touch CURRENT_TRUTH_INDEX`

`commit`

`push`

`declare doctrine`

It may:

`read explicitly approved source files`

`hash those files`

`copy small excerpts into report atoms`

`write new report files to a separate output folder`

`write JSONL ledgers`

`write Markdown summaries`

`write a receipt for the tracer run`

`mark DoesNotProve boundaries`

`stop on unsafe scope`

The key distinction:

`Writing reports is allowed.`

`Changing source is not allowed.`

# 2. Recommended first implementation shape

Use PowerShell first.

Reason: the user’s house and workflow are Windows/PowerShell-heavy, previous receipts and hashes are already PowerShell-shaped, and PowerShell has native commands that fit the house’s custody model. Microsoft’s `Get-FileHash` computes a hash for a file using a specified algorithm and defaults to SHA256, which fits the source-set and artifact identity checks. ([Microsoft Learn][1]) PowerShell also has `ConvertTo-Json`, which converts .NET objects to JSON strings, useful for writing machine-readable ledgers. ([Microsoft Learn][2]) If transcript logging is needed during a later live run, Microsoft’s `Start-Transcript` records commands and console output to a text file, but that should be optional and bounded because transcript noise can become proof furniture. ([Microsoft Learn][3])

Python can be a second-stage tool if semantic grouping becomes heavy. Python’s standard `json` module can validate and pretty-print JSON from the command line, which is useful for checking report files later. ([Python documentation][4])

But V0.1 should not need embeddings, vector databases, external packages, or internet access. V0.1 should be deterministic and boring.

PowerShell V0.1 should do:

`path validation`

`hashing`

`text reading`

`atom splitting`

`regex/keyword trigger detection`

`JSONL writing`

`Markdown report writing`

`receipt writing`

That is enough.

`AtomId if applicable`

`WasSourceModified: false`

`PartialOutputsWritten`

`SafeToRerun`

Errors should not delete partial outputs.

Partial outputs should be marked:

`PARTIAL_REPORT_NOT_FINAL`

The tool should write:

`RUN_ABORTED_RECEIPT.md`

if it fails after preflight.

If it fails before preflight output, PowerShell console output may be all that exists.

No cleanup of partial reports unless user explicitly authorizes later.

# 22. Safety stop language

The tool should have hard-stop messages like:

`STOP: source path is a directory; whole-house crawl blocked.`

`STOP: excluded parked drift file included.`

`STOP: mutation parameter detected.`

`STOP: output path collides with source path.`

`STOP: ACTIVE_GUIDES/CURRENT_TRUTH_INDEX path included.`

`STOP: source hash mismatch; rerun only with explicit hash-discovery authority.`

`STOP: script execution requested; tracer is read-only.`

No soft phrasing.

# 23. What the tool must not “helpfully” do

It must not:

auto-create missing source files.

auto-repair manifest.

auto-rewrite bad claims.

auto-normalize source.

auto-move outputs if path is unsafe.

auto-include nearby files.

auto-follow links.

auto-fetch web sources.

auto-open repo.

auto-interpret all markdown links as source.

auto-upgrade concept group to rule.

auto-delete residue.

auto-retry with broader scope.

Every one of those “helpful” moves becomes drift.

# 29. Batch T12 verdict

The read-only tool spec is now bounded.

Sewn rule:

`The first local Gate Trigger Tracer tool must be a manifest-driven, read-only, report-only small-lab replay tool. It may hash, read, atomize, detect expected and actual gate triggers, compare gate paths, scope claims, create pass-forward packet ledgers, group deterministic concept families, classify residue, check invariants, and write reports. It may not mutate source, execute commands, clean, delete, archive, dedupe, install, commit, push, crawl the whole house, start a watcher, automate intake, write doctrine, rewrite ACTIVE_GUIDES, or rewrite CURRENT_TRUTH_INDEX.`

Second sewn rule:

`The tool must refuse helpful drift. No recursive scan, no auto-repair, no auto-include nearby files, no web fetch, no source rewrite, no doctrine promotion, no graph database, no semantic grouping in V0.1.`

Third sewn rule:

`The tool’s output receipt proves only that the tracer run produced bounded reports from the declared source set. It does not prove source truth, content quality, runtime behavior, doctrine, whole-house readiness, or automation safety.`

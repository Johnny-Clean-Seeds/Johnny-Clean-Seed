Yes. This is a major rule. You found the bigger recursive-system hazard.

The danger is not only “a helper script might fail.” The bigger danger is:

A helper changes something, then another helper trusts that changed thing, then the system adjusts itself from its own bad output, and the bad logic becomes self-reinforcing.

So the dry-run boundary cannot be local-only. A receptionist helper cannot say, “I only touched receptionist stuff.” If its output later feeds routing, custody, gates, ledgers, selectors, or other helpers, then its dry-run must follow that impact outward.

I locked this as the **Recursive Dry-Run Expansion Gate**.

Core rule:

A helper is not cleared just because it passes inside its own room. It must pass through its full impact cone: local task, direct dependents, upstream authority checks, sibling helpers, parent room, cross-room effects, and whole-house simulation where needed.

Practical version:

Every helper must declare:

`scope`
`read set`
`write set`
`side-effect markers`
`downstream dependents`
`upstream authorities`
`files it can influence later`
`files that can influence it`
`what it does not prove`

Dry-run sequence should escalate like this:

`local dry-run`
→ `same-family dry-run`
→ `dependent-helper dry-run`
→ `room-level dry-run`
→ `cross-room impact dry-run`
→ `whole-house no-action simulation`
→ `residue check`

The key line is this:

`Outside this helper’s range is not a stop condition if its output can affect other helpers.`

That means the system must follow the effect chain, not the helper’s self-declared comfort zone.

The repeated failures already point to helper-generation weakness. The new rule prevents that weakness from becoming self-running automation.

RULE CARD:


CONSOLE POLLUTION INCIDENT RULE

Status:
LOCAL_RULE_CARD / CURRENT_WORKFLOW_ONLY / NOT_DOCTRINE / NO_PHYSICAL_ACTION_AUTHORITY

Purpose:
Prevent accidental pasted report text, terminal output, or prompt text from being mistaken for project damage.

Problem:
Sometimes report output or copied terminal history can be pasted back into PowerShell. PowerShell then tries to execute lines such as:

PS C:\Users...
contract_gate_passed: True
output_sha256: ...
final_verdict: ...
physical_actions: move=0 delete=0 rename=0 route=0 execute=0 commit=0 push=0

This creates console errors, but those errors do not automatically mean project files were changed.

Rule:
Accidental pasted report/output text into PowerShell is classified first as:

CONSOLE_POLLUTION_INCIDENT

unless there is evidence of successful file mutation, route, cleanup, commit, push, execution, or helper run.

Evidence that usually means console pollution only:

* “The term is not recognized”
* ParserError
* Get-Process errors caused by pasted `PS C:\...` prompt text
* Failed attempts to execute report labels such as `contract_gate_passed:`
* Failed attempts to execute output lines such as `output_sha256:`
* No new successful script banner
* No physical action counts showing movement
* No commit/push success output
* No route/cleanup success output

Required response:

1. Stop commands.
2. Identify which shell was polluted.
3. Do not use the old/messy shell unless explicitly reauthorized.
4. Determine the last verified successful script output.
5. Confirm whether any successful mutation occurred.
6. If no mutation occurred, classify as console pollution only.
7. Clear only the active clean shell screen if safe.
8. Resume from the last verified successful object, not from the pasted error noise.

Forbidden response:
Do not claim file damage just because PowerShell printed errors.
Do not treat pasted output labels as real helper execution.
Do not switch to the old shell to “escape” the polluted console.
Do not clear evidence shells unless explicitly authorized.
Do not continue from the polluted lines as if they were valid state.

Safe recovery command for active clean shell only:
Clear-Host
